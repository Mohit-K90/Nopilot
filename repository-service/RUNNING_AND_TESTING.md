# Repository Service – running and testing

## 1. Environment variables (nothing secret lives in application.yaml any more)

| Variable | Required | Purpose |
|---|---|---|
| `JWT_SECRET` | yes | Base64 secret, **identical to user-service** |
| `DB_PASSWORD` | yes | PostgreSQL password |
| `DB_USERNAME` | no (default `postgres`) | PostgreSQL user |
| `GITHUB_TOKEN` | no | Raises GitHub API limit from 60 to 5000 requests/hour. A token with **no scopes** is enough for public repos |

IntelliJ: Run Configuration → Environment variables. PowerShell: `$env:JWT_SECRET="..."; $env:DB_PASSWORD="..."`.

## 2. Build and run

```bash
./mvnw clean package -DskipTests          # compile + package
./mvnw test -Dtest='GitHubUrlTest,SourceFileFilterTest'   # pure unit tests, no DB needed
./mvnw spring-boot:run                    # needs PostgreSQL + env vars
```

`RepositoryServiceApplicationTests.contextLoads` (generated by Spring Initializr) starts the whole
application, so it needs PostgreSQL and the env vars above; plain `./mvnw verify` fails without them.

Hibernate (`ddl-auto: update`) will create the new table `repository_files` and add the new nullable
columns to `repositories` automatically. Existing rows stay valid.

## 3. Postman

Import `NoPilot-RepositoryService.postman_collection.json` and run it with the Collection Runner
(user-service on :8081, repository-service on :8082). Folder order matters; each request has assertions.
Change the `githubUrl` collection variable to test another public repository.

## 4. Endpoints

| Method | Path | Success | Notes |
|---|---|---|---|
| POST | `/api/repositories` | 201 `{repositoryId,status:"PENDING"}` | unchanged contract |
| GET | `/api/repositories` | 200 list | only the caller's, newest first |
| GET | `/api/repositories/{id}` | 200 | includes ingestion summary |
| GET | `/api/repositories/{id}/files` | 200 | 409 unless status is READY; no file contents |
| POST | `/api/repositories/{id}/ingest` | 200 | synchronous; 404/429/502/422 on GitHub problems |
| DELETE | `/api/repositories/{id}` | 204 | removes the row and its stored files; 409 while INGESTING |

Errors always look like `{"timestamp","status","error","message"}` (same as user-service).

| Situation | Status |
|---|---|
| Invalid URL / invalid body / bad UUID | 400 |
| Missing, invalid or expired JWT | 401 |
| Not found **or belongs to someone else** | 404 |
| Duplicate registration; ingest already running; files requested before READY; delete while INGESTING | 409 |
| Nothing usable in repo / repo empty / too large for GitHub to list | 422 |
| GitHub rate limit (with `Retry-After` header when known) | 429 |
| GitHub unreachable / unexpected GitHub error | 502 |
| Anything unexpected | 500 (generic message, details only in the log) |

A GitHub repository that does not exist returns **404 from the ingest call** with a message that starts with
"GitHub could not find…"; the local repository record is kept and set to `FAILED` with `failureReason`.

## 5. Status flow

```
register -> PENDING
ingest   -> INGESTING -> READY    (files saved, counts filled in)
                      -> FAILED   (failureReason set, stored files removed)
```
Invariant: a repository has rows in `repository_files` **if and only if** it is READY.
A restart while INGESTING cannot leave a repository stuck: on startup any INGESTING row becomes FAILED.

## 6. Database consistency checks (psql, database `nopilot_repositories`)

```sql
-- status / counts overview
SELECT id, status, file_count, total_size_bytes, skipped_file_count, default_branch, failure_reason FROM repositories;

-- stored files match the repository's file_count / total size for READY repos (expect 0 rows)
SELECT r.id FROM repositories r
LEFT JOIN (SELECT repository_id, COUNT(*) c, COALESCE(SUM(size),0) s FROM repository_files GROUP BY repository_id) f
  ON f.repository_id = r.id
WHERE r.status = 'READY' AND (COALESCE(f.c,0) <> r.file_count OR COALESCE(f.s,0) <> r.total_size_bytes);

-- files for non-READY repositories (expect 0 rows)
SELECT f.repository_id FROM repository_files f JOIN repositories r ON r.id = f.repository_id WHERE r.status <> 'READY' GROUP BY 1;

-- orphaned files after deletes (expect 0 rows)
SELECT f.repository_id FROM repository_files f LEFT JOIN repositories r ON r.id = f.repository_id WHERE r.id IS NULL GROUP BY 1;

-- eyeball content: paths + sizes + first line
SELECT path, size, language, left(content, 60) FROM repository_files WHERE repository_id = '<id>' ORDER BY path;
```

## 7. Limits (application.yaml → `nopilot.ingestion`)

max 200 files, 100 KB per file, 5 MB total. When a repo has more relevant files than that, README → build/config
files → source (shallow paths first) → docs are kept in that order. Files that are not valid UTF-8 or contain NUL
bytes are treated as binary and skipped. `skippedFileCount` = relevant files that were not stored.

## 8. Known limitations (deliberate, to keep the design small)

* Public repositories only (a token would allow private ones but that is untested).
* Ingestion is synchronous; a very large repo can take tens of seconds. The hook for RabbitMQ is `IngestionService.ingest`
  (publish a message instead of calling `runIngestion`) and the place to notify the AI Service is right after `IngestionStore.saveSuccess`.
* GitHub truncates tree listings of huge repositories (~100k entries); those are rejected with 422 rather than partially ingested.
* A default branch whose name contains `/` is not handled specially.
* No DB-level unique constraint on (user, owner, repo): duplicates are checked in the service, so two simultaneous registrations could both succeed.
